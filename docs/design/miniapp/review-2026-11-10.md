## 结论与确定范围

**保留 v1 方向，补齐技术与交互约束后继续实施；不把原文或 HTML 原样视为完整验收样本。** 照片主导、白色内容面、深绿操作、系统中文字体，以及菜谱/计划/清单/家庭的信息架构彼此一致，符合家庭厨房任务。无需另起视觉体系或增加组件库。

原规范对权限、未知数量、私有图片、自动保存、原请求恢复和分阶段交付的约束较完整；主要缺口是：原则没有充分落实到每页的组件职责、字段错误、离开/关闭规则、微信无障碍及字体适配。当前实现也存在与目标不一致的部分，不能因使用 Wot 就判定符合最佳实践。

本轮已将确定的规则补入 [README](README.md)，并添加 [P-01～P-16 逐页规范](page-specs.md)。保留用户认可方向，技术/可访问性修正对应 D-11 / D-12；不声称用户另行批准了一个全新视觉版本。规范现在可作为后续实施依据，生产完成仍需真实渲染与业务验收。

## 发现与处理

### R-01 · P1：未提交输入与“原请求恢复”没有分清

- **依据**：[编辑页](../../../miniapp/src/pages/recipes/edit.vue) `reload()` 已确认丢弃，但页面底部调用 `page.back`；[共享返回](../../../miniapp/src/features/recipes/use-recipes-page.ts) 直接 `switchTab`。未发送的 draft 不属于 `recipes.pending`，离开后卸载编辑页会丢失它。[导入输入](../../../miniapp/src/pages/imports/submit.vue)也在隐藏/卸载时清空未提交文本。
- **影响**：用户可能以为“恢复请求”能恢复尚未发送的长菜谱。保存请求失败恢复正确，也不能弥补主动返回时的输入丢失。
- **文档处理**：README 4.1 明确未提交/结果未知/已成功三态，P-09/P-10 要求应用内主动丢弃前说明并允许返回编辑。保留原 ID 恢复和隐私清理，不新增离线自动草稿系统。
- **实施仍需**：覆盖返回、重新加载、弹层关闭，以及系统离开不可保证的边界；不能为了保留草稿而让已失权家庭内容继续可见。

### R-02 · P1：长表单失败只给综合错误，无法定位修正

- **依据**：[编辑页](../../../miniapp/src/pages/recipes/edit.vue) `save()` 捕获 `input()/parseInput` 错误后仅设置 `copy.invalidRecipe`；标题、食材各字段、步骤主要由普通 text + Input/Textarea 组成。家庭名/邀请码也缺少可验证的字段关联。Wot v2 [Form](https://wot-ui.cn/component/form.html)已提供 schema、FormItem prop 和字段提示。
- **影响**：长食材表单某一行出错时，用户只能反复猜测；页面末尾错误可能在键盘或滚动区外。
- **文档处理**：README 4.1 和 P-02/05/09 确定字段/行错误、保留输入、首错定位；使用 v2 `schema`，不混用 v1 rules，不强加 Zod 依赖。
- **实施仍需**：从现有校验中保留可定位的错误信息并接到表单，检验键盘打开时也可到达错误。仅包一层 Form 而继续输出同一段笼统提示不算完成。

### R-03 · P2：HTML 语义和外层 ARIA 不能证明微信读屏可用

- **依据**：多个现有页面使用 `role="status"` / `role="alert"`。微信官方 [ARIA 组件说明](https://developers.weixin.qq.com/miniprogram/dev/component/aria-component.html)说明其角色属性为 `aria-role`，且部分角色在移动端可能无效。Wot 2.4.0 的 Input/Search 内部有实际 input，但当前类型/模板没有证明页面外层字段标题和错误自动关联到了这个节点。
- **影响**：H5/jsdom 断言成功时，微信仍可能读不出字段名称、选中状态或异步错误；源码里有 ARIA 不足以放行。
- **文档处理**：增加平台语义、内部节点核对和最小原生例外规则；保留已具备无障碍支持的原生确认框，不为统一外观重做它。
- **实施仍需**：分别验证 iOS/Android 微信读屏，确认名称、焦点顺序、状态、错误和恢复动作；不能简单把所有 `role` 全量改为 `aria-role` 后宣布通过。

### R-04 · P2：大字号只有换列判断，尚缺文字缩放证据

- **依据**：[theme.css](../../../miniapp/src/styles/theme.css) 正文/Input/Button/标题使用固定 px；[菜谱列表](../../../miniapp/src/pages/recipes/index.vue)仅根据 `fontSizeSetting >= 20` 或宽度切单列，未在此逻辑中放大文字。导入两页另用局部 `40rpx` 标题。微信[适老化指南](https://developers.weixin.qq.com/miniprogram/design/elderly.html)要求结合平台字体设置适配自绘内容。
- **影响**：改成单列只增加空间，尚不能证明兑现“大字号可读”；同一阈值也不能完整代表不同系统档位。
- **文档处理**：标准字号与缩放行为分开，明确文字、控件随设置增长，原生导航与自绘内容分别验证。
- **实施仍需**：核对当前平台/运行包的字号缩放机制，再补必要适配，确认不会重复缩放。真机证据应包含标准、放大和较大档位下的正文/输入/按钮，不只有双列变单列。

### R-05 · P2：令牌单独合格，部分前景/背景组合不合格

按 sRGB 相对亮度与 `(L亮 + 0.05) / (L暗 + 0.05)` 计算，未计透明度；普通文字阈值为 4.5:1，必要控件轮廓为 3:1。

- 主文字 `#202923`：对白约 **14.97:1**；品牌绿 `#216840`：对白约 **6.73:1**，均可保留。
- 辅助文字 `#667269`：对白 **5.03:1**、对页面底色 **4.72:1**，对选中浅底仅 **4.44:1**；不能把同一 muted 色无条件用于所有表面。
- 原警示候选 `#9B6A1A`：对白 **4.70:1**，对页面底色仅 **4.41:1**。已将规范改为 `#8A5D17`，对白/页面底色/选中浅底分别约 **5.74 / 5.39 / 5.07:1**。
- 分隔线 `#E5EAE6`：对白约 **1.22:1**，可作装饰分隔，不能充当必要输入/勾选框边界。新增边界令牌复用当前代码的 `#818C84`，对白/页面底色约 **3.49 / 3.28:1**。

**文档处理已完成**：锁定组合与角色，不换整套配色。生产代码、透明叠层、图片上的图标和组件禁用/按下态仍需实测，不能把计算结果泛化到所有截图。

### R-06 · P2：预览存在低于项目要求的点击区

- **依据**：实际浏览器 390px 预览中，首页标签按钮高 **34px**，排序高 **32px**；320px 下仍双列，菜名 **14px**。四种首页宽度未出现整页横向溢出，但这不等于点击和阅读要求通过。
- **文档处理**：保留 README 的项目 **44×44** 要求，明确原型不是尺寸豁免；小视觉元素可扩展热区，窄屏可单列。不要把 WCAG 2.2 AA 的 24px 最低要求误称 44px。
- **实施仍需**：除主按钮外，还检查 Wot 内置清空、收藏、评分、日期、勾选和关闭按钮；库默认大小不自动满足本项目门槛。预览源文件本轮保留，仍用于已认可构图，差异已显式登记。

### R-07 · P2：组件职责与风格尚未完全统一

- **依据**：家庭首页现在用同规格 Button 堆入口；成员移除/转移/返回也主要都是 info Button。AI 两页仍用原生按钮/textarea 和局部 rpx 样式，其余九页已用 Wot/共享主题。[详情](../../../miniapp/src/pages/recipes/detail.vue)会把每张图逐一大图置于正文前，未知数量统一显示“适量 / 未注明”，两者都比原型/业务语义更含糊。
- **文档处理**：统一主/次/危险操作，导航行优先 Cell，长表单/状态反馈统一，平台能力作为明确例外；P-08 保留原文，不把未知一律解释为适量，避免全部大图淹没正文。
- **实施仍需**：九页调整归 #20，AI 页面归其相应业务工作；有意的原生分享/确认差异可以保留。受控标签接口缺失时，明确标签输入也是合理适配，不为了还原 chip 新增后端。

### R-08 · P2：文档/工具证据有历史与版本混用风险

- **依据**：README 原本要求从“尚未接入”开始，而当前声明、锁文件和安装均为 Wot 2.4.0；历史工单文本仍有当时的未提交 #8 描述。全文 Cell 示例出现 `<wd-button plain>`，2.4.0 Button 类型采用 `variant`；CLI Cell 摘要遗漏实际支持的属性。
- **文档处理**：README 明确当前集成；S-CODE 保留不可变历史，S-REVIEW 记录当前工作区。全局主题沿用 `page, .wd-root-portal` 即符合官方实践，ConfigProvider 用于局部/动态需求，不一律强制包装。
- **实施仍需**：核对安装源码/类型、具体文档段落与运行结果；Popup 的 `v-model` 不能推成所有组件都 `v-model:visible`。不自动升级依赖、改第三方源码或覆盖 llms 快照来掩盖差异。

### R-09 · P2：后续页面只有方向，尚不是完整交互交付物

- **依据**：预览计划只有固定一周和三餐，购物只有一张演示清单，评论是固定样例，评分/加购也只是内存交互。现有业务规范却要求其他餐次、多清单、整数评分可撤销、权限、并发和可恢复部分加购。
- **文档处理**：P-12～P-16 明确跨日期/餐次、清单切换、条目编辑、未知量、部分完成、评论权限、评分撤销和危险生命周期的必要流程；与原业务设计交叉引用。
- **实施仍需**：各业务票补页面/选择视图、具体状态及真实契约证据，再开放导航。这里补齐任务要求不表示这些模块已实现，也不增加 #20 的外部阻塞。

## Wot 采用结论

- **保留**当前 2.4.0、easycom、按需类型及应用主题。全局语义变量 → 组件变量 → 必要且受控的样式例外；不新增第二套 UI 框架。
- **表单**采用 v2 Form/FormItem 的 schema 能力表达现有校验与错误；可见 title 仍需核对真实可访问名称。数字空值、私有上传、版本和恢复由业务服务负责，组件不替代这些边界。
- **弹层**区分无草稿菜单、输入表单、危险确认和长时任务；具体使用 Popup、Picker、Dialog 或原生能力，按已核实的 API 和任务需要选择。Popup 安全区、滚动穿透、懒渲染尺寸和关闭行为需运行验证。
- **复用**实际共有的菜谱条目、食材/步骤、成员、恢复状态；不为设计文档先造通用组件平台。尚未交付的图表、动效、深色模式和新统计不进入当前范围。
