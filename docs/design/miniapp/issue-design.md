# 小程序 UI 工单约定

适用：新页面、新交互、视觉改版与既有页面重构。[规范入口](README.md)、[来源 ID 与决定 ID](sources.md)。GitHub 表单见 `.github/ISSUE_TEMPLATE/miniapp-ui.yaml`。

## 发布前必须具备

1. **用户结果**：明确触发条件与改变后的可见行为；指出已有功能、新能力与非目标。
2. **来源与批准**：链接本基线版本、具体 D-ID/S-ID、相关业务设计章节、实际基准提交与页面；新视觉决定要有参考职责和确认状态。优先使用不可变提交链接，不能只写“见聊天”“按 skill 最佳实践”。
3. **范围**：列出影响的页面、导航/调用方、组件、文案、测试和依赖；仅在确实必要时扩展契约。原型独有元素逐一标记采用/不采用。
4. **状态与验收**：正常、加载、空、失败、权限失效、请求恢复、编辑冲突、媒体失败；明确不适用状态及原因。列出手机宽度、大字号、安全区、点击区域、实际截图、业务回归和 `task -d miniapp check`。
5. **真实依赖**：只有缺失且本票无法交付的业务/接口才建立原生 blocked-by 关系；“相关 issue”不自动是 blocker。不存在 blocker 写 `Blocked by: None`，并说明为什么可以开始。测试/构建/截图是本票交付项，不能仅因尚未执行就标为 needs-info。

当明确需要新的供应商能力、账户/预算或真实云资源且它影响本票核心结果时，必须诚实记录，不能为了不 blocked 虚构能力。能通过收窄为已有接口的 UI 重构解决，就把新业务保留给原功能票。

`ready-for-agent` 表示来源和范围足以开始；不表示已实现、测试已通过或自动获准生产部署。创建后回读标题、正文、标签和原生 `blocked_by` 列表。没有用户授权不关闭旧 issue、不删除旧依赖。

## 最小正文

```markdown
## What to build

[谁在什么页面完成什么操作，改造后的可见结果。]

## Design evidence

- 基线：[固定提交的 docs/design/miniapp/README.md]；D-xx / S-xx。
- 业务规则：[设计章节或已交付 issue]。
- 当前代码：[固定基准提交/页面/契约]。
- 原型适配：[采用的视觉特征；不采用的模拟行为]。

## Scope and boundaries

[页面、调用方、组件、文案与测试；本票明确不引入的新业务。]

## Blocked by

None — [已有事实为什么支持立即开始；或列出真实未满足依赖。]

## Acceptance criteria

- [ ] 用户可以完成本票结果；相关权限、恢复和并发语义保持。
- [ ] 相关状态矩阵覆盖，320/375/390/430px 与大字号无溢出/遮挡。
- [ ] 关键点击目标、对比度、标签与异步反馈满足基线。
- [ ] 既有回归与 task -d miniapp check 通过，附实际渲染截图及差异记录。

## Execution constraints

[云账户、部署、数据迁移与业务契约是否在范围内；不自动扩大授权。]
```

## 已有功能重构的就绪边界

基于已推送 `0dc31abfff4cfd53df90ad5a8161ed7498c0eaa2`，#1–#7 页面足以独立完成样式、组件和导航改造。#8 的本地未提交工作不作为输入；#9–#19 不作为前置。后续它们自己的工单引用相应页面模式即可，不以本票关闭作为一律必需的前置。

若待执行分支已合入新模块，在实施计划里记录实际代码变化；不要擅自把未验收的新业务算进原 UI 工单的完成范围。
