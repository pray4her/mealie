# 逐页与组件规范 v1

2026-11-10 技术审阅补充，继承 [README](README.md) 的视觉令牌、交互和验收要求。依据 D-01/02/03/04/05/06/08/10/11/12，来源 S-BUSINESS / S-PREVIEW / S-WOT / S-WECHAT / S-A11Y / S-REVIEW。这里只细化既定业务的呈现方式，不批准新模块提前上线。

当前路由有 11 页：#20 的 9 页和 AI 导入 2 页。以下“需补”指本次静态审阅发现的实施或证据缺口，不代表已修复。代码快照、查询与浏览器观察见[审阅报告](review-2026-11-10.md)。后续页面尚未有生产实现，按对应业务工单补完交互和状态证据；不反向阻塞既有页面重构。

**v1.1 实施裁定（2026-11-11）：**[Figma 对照稿](https://www.figma.com/design/M1kY55jqZwUQm6gh2woCam)及[节点映射](../../../miniapp/ops/ui-visual-v11/figma-nodes.json)辅助对照，仓库规范继续作为事实来源。Figma 320 大字稿仍待修正，Starter 工具额度已用尽，不作为已冻结或通过的证据。微信截图、字号/布局采样与候选状态见[本轮记录](../../../miniapp/ops/ui-visual-v11/README.md)。

- 列表契约只有 `items` / `nextCursor` 以及 `query` / `tag` / `favoritesOnly`，不提供标签集合、全家庭总数或自定义排序。首页不编造快捷标签和总数；“最近添加”为静态顺序说明，“已显示 N 道”为当前加载条数，精确标签在筛选弹层输入。
- 标准正文/输入最低 16px，问候 27px；系统有效放大倍率只在单一根字号路径应用。320 标准态保留两列照片，大字态改单列；短字段按可用宽度和大字状态重排。
- 选中范围用字重、短下划线和 `aria-pressed`，视觉文案不带“（已选）”；卡片打开与44px收藏操作互为同级目标。
- 有修改的编辑/导入/家庭表单离开前确认，不增加跨页或落盘草稿。页面仍存活时后台返回重新鉴权后保留当前输入，卸载、退出登录和失权清理；既有已发请求及图片恢复不变。微信官方返回询问不拦截 iOS 侧滑，强退也可能丢失未提交输入。

**修复进度更新：**R-03～R-07 的代码与浏览器布局修正见[实施证据](../../../miniapp/ops/ui-accessibility-2026-11-10/README.md)；下文“审阅”保留发现时的描述。当前 Wot 2.4.0 的原生 ARIA 例外以 README 第 4 节为准：输入使用原生节点，操作使用 `HomeAction`，继续复用 Wot 外观/Cell/Popup。R-01/02 与设备验收仍开放。

## 当前页面

### P-01 微信登录 · `pages/account/login`

- **职责与层级**：产品名、简短用途、微信登录；一个主按钮，不增加手机号或密码表单。
- **组件**：`wd-button` 的 `loading` / `disabled`；微信身份流程复用现有 auth。品牌标志可以装饰，按钮必须有文字。
- **交互与状态**：恢复登录、登录中、拒绝/失败可重试、身份成功但家庭读取失败分别说明；有邀请时优先续接加入。不能登录成功后停在没有下一步的界面。
- **审阅**：结构符合方向。需在真实微信确认请求状态与登录后的页面跳转、读屏反馈，不能只凭按钮源码判断。

### P-02 家庭引导 · `pages/family/onboarding`

- **职责与层级**：清楚区分“创建家庭”和“已有邀请”；创建表单为主任务，加入入口为次操作。已有家庭直接进入家庭内页面。
- **组件**：`wd-form` / `wd-form-item` / `wd-input` / `wd-button`，家庭名称保留现有规范化和长度校验。
- **交互与状态**：字段错误就地显示；创建中防重复；结果未知时显示原家庭名称和“恢复创建请求”，不可改名另建。守卫失败有重试与退出登录。
- **审阅**：恢复语义已表达；当前输入旁的普通 `text` 与页面末尾 message 不足以证明字段关联和错误定位，需补表单及读屏证据。

### P-03 家庭首页 · `pages/family/home`

- **职责与层级**：真实家庭名、本人角色、成员和邀请入口；普通成员不展示所有者专属操作。没有可靠总数就不显示统计。
- **组件**：入口优先 `wd-cell-group` / `wd-cell`，角色用轻量文字/Tag；退出登录为低强调次操作。原生 TabBar 承担菜谱/家庭切换。
- **交互与状态**：首次加载、失权、家庭读取失败、退出中的状态清楚；刷新后角色变化同步到入口。
- **审阅**：现有权限与字段选择合理；当前相同规格的按钮栈与预览的入口列表不一致，实施时收敛为统一导航行，保留必要恢复出口。

### P-04 邀请家人 · `pages/family/invite`

- **职责与层级**：说明有效期/一次性含义，生成后突出分享及复制；已发邀请按状态和时间展示，撤销是明确的危险操作。
- **组件**：Button + 分隔行；分享可保留原生 `open-type="share"`，或在验证支持后使用 Wot 同等能力。无需为一致性重做微信分享界面。
- **交互与状态**：生成中、无邀请、分页、过期/已用/已撤销、撤销失败均有反馈；有效期从真实记录展示，不能只靠按钮可点暗示仍有效。恢复不重复生成邀请，token 不放入列表普通元信息。
- **审阅**：当前具备分享/复制及分页；生成与分享均为强操作时需随流程降低生成的强调，撤销样式与后果说明需补。过期后的点击反馈要实测。

### P-05 加入家庭 · `pages/family/join`

- **职责与层级**：有邀请则显示“已收到邀请”及加入确认；无邀请可粘贴邀请码。不向未授权用户额外泄露家庭/成员信息。
- **组件**：Form / FormItem / Input / Button；保留粘贴，避免验证码式逐格输入。
- **交互与状态**：过期、撤销、已使用、已在家庭、并发加入冲突与请求未知分别提示；登录续接不能丢邀请；结果未知时恢复原请求。已有家庭只给返回入口，不引入家庭切换。
- **审阅**：状态和边界合理；需补邀请码的字段级错误、输入名称及键盘/返回证据。

### P-06 家庭成员 · `pages/family/members`

- **职责与层级**：昵称、本人/所有者标记、必要的身份辨识；长昵称/ID可换行，不抢占主操作位置。
- **组件**：成员业务行 + 次按钮；移除与退出家庭用危险文案/样式，转移所有权说明对象和权限后果。现有 `uni.showModal` 可以保留，不强制改为 `useDialog`。
- **交互与状态**：确认后才提交；成员移除/所有权变化时重新校验，未知请求按既有 membership 恢复；所有者先转移后退出，不能少展示此限制。
- **审阅**：已有确认对象及权限保护；移除、转移、普通返回当前都用 `type="info"`，需区分后果和强调，补长列表/同名成员与失权证据。

### P-07 菜谱浏览 · `pages/recipes/index`

- **职责与层级**：家庭上下文、主标题、搜索/添加、全部/个人收藏、标签条件、结果/分页、照片列表。添加菜单只列可用能力。
- **组件**：Search + Button；范围切换可用 `wd-tabs` 或两枚明确选中状态的轻量按钮，整站选定一种；这里是列表筛选，不增加第二组主导航。菜谱业务条目用 `4:3` 图片、两行标题和独立收藏按钮，避免嵌套点击触发两次。
- **交互与状态**：统一处理搜索确认、清空、范围和标签变更，重置相应游标；标签快捷项只能来自已交付受控集合，缺少接口时保留明确标签输入，不能把当前页标签说成全家庭标签。标题/标签有界匹配、下一段仍可查找的语义不变；本地数量标为“当前已加载”，不冒充总数。
- **审阅**：列表/收藏/恢复有基础。当前“标签输入 + 单独搜索按钮”是数据约束下的适配，不必为还原预览新增标签云接口；需记录与预览的差异。窄屏/大字号单列后，文字自身仍须增大。内置清空/收藏/筛选的命中区域逐一检查。

### P-08 菜谱详情 · `pages/recipes/detail`

- **职责与层级**：封面/图片 → 标签/全称/真实作者 → 已知时间/份数 → 简介 → 食材 → 编号步骤 → 已交付互动。多图不能无上限把正文挤到长图墙后；保留全部图片的可达预览入口。
- **组件**：菜图及原生预览、食材两列业务行、步骤正文、收藏/编辑按钮；不要把每个步骤套 Card。封面和原图用途分开，固定占位避免跳动。
- **交互与状态**：图片失败不阻断文字；临时链接到期重新授权，失权先隐藏；未知数量不一律改写成“适量”，优先保留原文，必要时标“未注明数量”。缺少基数时关闭换算，不改菜谱原始数量。
- **审阅**：信息与业务边界符合方向。当前逐张大图置顶、未知数量统一“适量 / 未注明”需收敛；当前阶段保留收藏/编辑，不提前出现计划/购物/评分假按钮。

### P-09 菜谱创建/编辑 · `pages/recipes/edit`

- **职责与层级**：标题/简介、可选份数/时间、结构化食材、步骤、标签、图片；保存为主操作，增加/移除行为留在各自分组。图片与文字若分别保存，要在操作附近解释。
- **组件**：Form / FormItem / Input / Textarea / Button；长食材用上下布局，数量/单位在空间足够时同排。复用当前 parser/业务校验；不把未知值交给默认会初始化数字的计数器。
- **交互与状态**：错误须指出第几行哪个字段，保留输入并定位；删除行、重新加载和主动离开遵循防误丢规则。原保存结果未知时锁住新提交并恢复原 ID；版本冲突不自动覆盖，明确重新加载会丢弃哪些输入。
- **媒体边界**：先保存文字再加图片是当前能力限制，明确说明；继续用现有受控上传/审核服务。若使用 `wd-upload`，先验证自定义上传/预览/删除与私有授权、失败补偿的衔接，不能将 `action` 直连公开存储替代现有链路。
- **审阅**：字段保留、原请求恢复及重新加载确认方向正确；目前 `parseInput` 失败只返回综合错误，且返回菜谱直接离开，字段定位和未提交修改确认需补。新建页不承诺“一次保存同时完成图片上传”。

### P-10 AI 输入 · `pages/imports/submit`

- **职责与层级**：一道菜的原文、第三方处理/留存/自动保存说明、一个同意并导入按钮；文字、图片、网址按能力分别交付。
- **组件**：与其他表单相同的 Form / Textarea / Button；告知用普通正文，不用低对比小字承担同意含义。输入上限按实际契约，字节限制不能仅用字符 `maxlength` 冒充。
- **交互与状态**：空/过长/不支持内容就地提示；请求未知恢复原输入和请求，不开启第二次导入；离开前说明尚未提交输入的处理。无配额/功能停用仍可返回手动建菜谱。
- **审阅**：当前业务告知与恢复有依据；仍用原生表单和局部 `40rpx` 标题，与其余页的 Wot/24px 标题体系不一致，应在 AI 对应工作中收敛，不能算 #20 九页未完成的前置条件。

### P-11 AI 任务 · `pages/imports/status`

- **职责与层级**：真实状态和下一步；成功为“已保存”，查看为主、核对编辑为次；失败/取消可重新导入，不把新任务误称原请求重试。
- **组件**：持续状态文字与 Button；需要时用一个 Loading 或 Steps，不使用无法测量的百分比。返回菜谱不等于取消任务。
- **交互与状态**：排队/解析审核、查询失败、任务失败、取消中、取消与成功竞争、成功、失权分别处理；最终展示服务端终态。关闭/隐藏停止页面轮询，重进按任务 ID 恢复；不要承诺取消已经发生的供应商费用。
- **审阅**：自动保存及恢复语义合理；控件/字号需与 P-10 一起统一。取消操作不能被其他 loading 状态冒充已取消，需有终态竞争证据。

## 后续页面与组合交互

### P-12 计划页与安排一餐 · #11

- 周日期条和当日餐次列表复用照片/文字层次；早餐、午餐、晚餐、**其他**均保留，同餐多菜。
- 日期条需能到达其他周/日期，区分“今天”和“选中”；窄屏允许日期条独立横滚，每个日期保持命中区域。使用家庭本地 `YYYY-MM-DD`，不从 UTC 截取日期。
- 安排流程明确菜谱、日期、餐次、目标份数及保存；短选择可用 Picker/SelectPicker，复杂菜谱搜索使用独立选择视图，避免多层弹层。份数属于计划快照，不改菜谱。
- 覆盖空日、空家庭菜谱、读/写失败、冲突、菜谱已删除/无权访问；手动选择加入清单，改计划不自动改清单。
- **审阅**：现有方向适合任务；预览缺其他餐次、跨周选择和编辑/移除流程，不能拿固定日期页面作为完整设计验收。

### P-13 多清单、清单详情与手动条目 · #12

- 先完成手动共享清单；页首明确当前清单并有切换入口，无清单时引导创建。不能把原型单张“这周采购单”变成唯一清单的数据约束。
- 清单选择复用 Cell + SelectPicker/Popup；条目用 Checkbox 与名称/数量行，已购独立分组，可撤销勾选。名称区域和勾选区共享连续热区，编辑另有明确入口，避免一次点击既编辑又勾选。
- 新建/编辑条目显示名称、数量/单位或原文；字段错误与其他表单一致。不新增必须由用户维护的品类体系；没有分类来源就不照搬原型固定分类。
- 勾选用条目级更新及忙碌/失败反馈；失败恢复确认状态，不伪装已完成。覆盖无清单、空清单、全部已购、条目被他人删除、版本冲突和失权。
- **审阅**：紧凑行与已购分组可保留；多清单、编辑/删除、并发失败行为需在此业务票补齐。

### P-14 菜谱/计划显式加购 · #13 / #14

- 确认来源、目标清单、份数和需手动核对的未知数量/单位；没有基准份数不展示伪换算。目标清单不隐式用上次别的家庭的选择。
- 选择流程可用 Popup + Form/SelectPicker，内容长时独立滚动；确认前不更改清单。完整配对标签、错误和主次按钮。
- 区分未提交、处理中、部分完成、全部完成和失败；显示已完成/待恢复范围，恢复同一操作 ID，用户主动再次加购才新建 ID。
- 数量合并由业务契约决定；UI 必须保留原文/贡献和来源，不自行按名称去重，不引入 AI 计算。
- **审阅**：衔接方向成立；原型直接 Toast 与名称去重不能作为最终交互/实现，部分成功是必须补的状态。

### P-15 评论与评分 · #15 / #16

- 放在详情正文之后；评论用纯文本行与分页，发表/编辑用 Textarea + 字段错误，取消保留/丢弃输入的规则一致。
- 本人编辑/删除、所有者删除按现有权限显示，删除先确认；长文换行，不能显示为 HTML 或让排序/分页丢失编辑中的输入。
- 评分用 `wd-rate` 的整数模式，明确“我的评分”和提交/修改结果；撤销有独立可发现动作，不能只依赖用户猜测再次点同一星。平均分只读、一位小数、带人数，无评分显示“暂无评分”。
- 覆盖无人评论/评分、提交失败保留输入、版本冲突、删除中、失权；统计来源为服务端，不从当前页评论/本地示例推算。
- **审阅**：业务边界清楚；原型五颗星和常驻样例评论缺少发表/编辑/删除/撤销及失败状态，后续票必须补齐。

### P-16 家庭设置、解散与账户注销 · 后续家庭生命周期工单

- 已交付设置显示真实字段；重命名/设置编辑复用表单、版本与错误规则，不能因原型“家庭资料”弹层虚构接口。
- 解散家庭与注销账户分别说明数据/共享内容/媒体后果，受所有者转移等业务前置约束；不能与“退出登录”“退出家庭”合并成同一动作。
- 使用独立、可完整阅读的危险确认流程，明确对象与不可逆后果；处理中、部分完成、失败恢复遵循业务操作记录，不先跳成功页再后台碰运气清理。
- **审阅**：总体业务设计已定义授权与清理规则，当前九页重构不提前开放这些入口；须在相应功能票补完整操作与恢复证据。

## 组件采用边界

- **直接复用**：Button、Input、Textarea、Search、Cell/CellGroup、Form/FormItem、Popup、Checkbox、Rate，以及确实需要的选择器/反馈组件。这里只锁定职责；具体 props/events/slots、类型注册和版本差异必须按 `miniapp/AGENTS.md` 查询。
- **业务组合**：菜谱图文条目、食材行、步骤、成员行、任务/恢复状态按实际复用提取。数量换算、权限、请求恢复不放进纯展示组件，不另建通用 Button/Modal/Form 框架。
