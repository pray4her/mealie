## 1. 来源顺序与批准边界

1. 用户明确需求与[已批准业务设计](../../superpowers/specs/2026-11-03-wechat-unicloud-design.md)决定数据、权限和业务行为。
2. 本规范及 `sources.md` 决定视觉、组件职责、排版、可访问性和工单证据要求。
3. HTML 预览决定已认可的视觉构图；其中静态样例、模拟行为和技术捷径不是生产业务规范。
4. 执行时核对实际代码、锁文件和官方文档；发现不一致时记录事实、作最小兼容调整，不把参考图或旧文档当作运行证据。

本次批准的是“照片主导、清爽实用的家庭厨房”方向与页面结构。`家常` 是此基线的产品展示名称；“林家的厨房”、成员、图片、评分、日期、食材和统计均为预览样例，不得写入真实用户数据。

用户认可不等于已完成浏览器视觉 QA、微信真机验收、Wot 兼容性验证或云业务验收。初始v1只建立规范与工单；后续v1.1已获授权实施生产页面修正，状态以上述候选记录为准。

## 2. 设计简报与参考锁定

为家庭成员设计中文微信小程序，让家人能查找、记录和共享菜谱，完成做饭、配餐和采购。

- **主参考：Kitchen Stories。** 保留真实菜图主导、直接的菜名层次、易读的食材与步骤；不引入其订阅、公开内容和营销布局。
- **局部参考：AnyList。** 仅借鉴购物条目的紧凑行布局和明确勾选反馈。
- **局部参考：Samsung Food。** 仅借鉴菜谱 → 餐次计划 → 显式加入购物清单的衔接。
- **产品自身：** 延续现有 `#216840` 深绿，用白色表面、中性文字和真实食物图片建立亲切感。
- **避免：** 大面积品牌色、装饰性渐变、无用途阴影、每段文字套卡片、把普通返回/退出操作全部做成绿色主按钮。

媒体策略：正式菜图来自家庭授权图片；列表统一 `4:3` 裁剪，详情可查看原图。无图、审核中、拒绝、链接到期或加载失败必须有稳定占位和相应反馈，不能换成另一道菜的照片。预览的 Unsplash 样例仅用于设计审阅，来源见预览 README。

## 3. 视觉令牌

令牌以已认可 HTML 的实际值为依据。实施时在应用自己的主题文件集中维护，并通过 Wot 官方主题接口映射；不要改 `uni_modules` 或第三方依赖源码。

| 角色 | v1 值 | 使用规则 |
| --- | --- | --- |
| 页面底色 | `#F7F8F7` | 内容背板；菜谱内容区可使用纯白 |
| 内容表面 | `#FFFFFF` | 列表、表单、弹层 |
| 主文字 | `#202923` | 标题、正文、重要数量 |
| 辅助文字 | `#667269` | 时间、作者、简短说明；不靠淡化承载关键状态 |
| 分隔线 | `#E5EAE6` | 内容分组；必要的控件边界须另验对比度 |
| 主操作/选中 | `#216840` | 主 CTA、选中导航与交互状态 |
| 主操作按下态 | `#184E30` | 交互反馈 |
| 选中浅底 | `#EAF3ED` | 已选标签和轻量选中状态 |
| 必要控件边界 | `#818C84` | 输入边界、未选勾选框等必须可辨识的轮廓；不替换普通分隔线 |
| 警示文字 | `#8A5D17` | 需用户留意的状态，须配文字，不作装饰；修正原候选色在页面底色上的对比度不足 |
| 危险文字候选 | `#B33F38` | 删除、移除、失败；实施时核验实际背景对比度 |

“品牌绿色”和“已完成”可以同色，但必须由图标、文字和结构区分含义。颜色不可作为唯一信息。错误与成功状态必须能从文案辨认。

令牌按前景/背景成对使用：辅助文字 `#667269` 仅用于白色或页面底色，不能直接放在选中浅底 `#EAF3ED` 上（约 4.44:1）；选中浅底上的文字用主文字或品牌绿。分隔线不承担必要控件边界。以上组合的计算依据见审阅报告，实际透明度、图片背景和禁用态仍须单独核验。

### 3.1 字体与尺度

使用系统中文无衬线字体：系统默认 → PingFang SC → Microsoft YaHei → Noto Sans CJK SC → sans-serif。首版不下载大体积中文字体，不混用装饰性字体。

- 页面标题：24px / 600；菜谱首页问候语可至 27px / 600。
- 区块标题：18px / 600。
- 正文、输入内容：16px / 400；做法步骤 16–18px、行高约 1.75–1.85。
- 条目标题：15–16px / 500–600。
- 操作文字与必要辅助说明：13–14px。关键数量不能缩小或弱化。
- 10–12px 仅限可省略的元信息；HTML 中这类字号不作为重要字段的生产要求。
- 字重以系统实际支持的 400/500/600 为主；不强制复刻 HTML 的 650。

重要信息在大字号下必须完整可读。正文不截断；菜谱浏览标题可限制两行，进入详情可读全称。布局应随文字增长，不用固定高度裁掉内容。

这里列的是标准字号；大字号适配必须让正文、输入、操作文字及相关控件随微信字体设置增大，再按内容换行/改列。仅检测字号后把菜谱改成单列不等于字体适配。按 [S-WECHAT](sources.md#s-wechat微信设计与无障碍)区分 iOS/Android 的标准字号和缩放信息，不用同一个固定阈值代表所有设备。原生导航/TabBar 与自绘内容分别验证；不新增应用内字号设置或离线草稿功能。

### 3.2 间距、形状与密度

- 采用 4px 基础间距；常用 8 / 12 / 16 / 20 / 24 / 32px。
- 页面水平留白 16–20px；预览默认 20px，窄屏 16px。
- 菜谱两列间距 12–14px；段落分区约 24–32px。
- 控件圆角 8–10px；菜图约 12px；大弹层顶部约 20–22px。
- 主按钮高约 48px；触摸目标以至少 44 × 44 逻辑像素为项目验收要求，小图标可扩展命中区域。
- 默认用留白、分隔线与文字层级分组。图片菜谱条目可以点击成组；食材、步骤、购物和设置不逐行套阴影卡片。

上述 px 是逻辑尺寸。uni-app 实施需按平台能力选择 px/rpx，不能将文字和所有点击区域按屏宽机械缩小。HTML 电脑外壳、侧栏、390px 固定审阅框不进入小程序。

## 4. 技术与组件职责

当前 Wot 2.4.0 的微信编译产物不会将外层 ARIA 透传到内部 Input/Search/Textarea/Button/Cell 原生节点。现行实施例外：输入使用带名称的原生 input/textarea 和共享令牌；普通操作复用 `HomeAction`（原生语义层 + Wot Button），家庭导航为原生语义层 + Wot Cell。视觉子树对读屏隐藏，避免重复目标；名称、禁用、忙碌和选中绑定到真实原生节点。它是当前版本的兼容修复，不是第二套 UI 库；库以后支持时，先核对产物和运行再收敛。Form 的字段校验职责不因该例外取消。

- 客户端保持 uni-app + Vue 3 + TypeScript，使用 `<script setup lang="ts">`、既有业务 composable 和客户端服务。
- **通用业务控件主库选择 Wot UI。** 表单、选择、搜索、弹层、反馈等优先用库已有能力；不为了改样式另外建立通用组件框架。
- 2026-11-10 当前 HEAD `4f4b56702d884d660ea49b92d88b1cc7e554e49f` 已接入 `@wot-ui/ui@2.4.0`，Sass `1.98.0`，easycom 和按需组件类型已存在；S-CODE 的“尚未接入”仅描述原工单历史起点。后续复核自己的锁文件与安装包，不重复安装、不混用旧 `wot-design-uni` v1 示例。首次引入或改变集成时的真实页面构建仍属于对应 UI 工单，不另设外部前置工单。
- 主题优先覆盖官方语义变量，再按需覆盖组件变量。全局主题可沿用应用主题文件中的 `page, .wd-root-portal`；局部主题或动态配置再使用 `ConfigProvider`，不要求为每页新增 Provider。弹层/portal 同样要获得主题。具体 API 以所选版本文档及安装包为准。
- 微信登录、授权、页面路由、图片预览、导航和可用 TabBar 保留微信/uni-app 原生能力。已接入的 uni-id 所需 uni-ui 模块继续保留；普通业务页面不要同时混搭多套组件视觉。
- 仅提取被多页实际使用或明显需要独立职责的业务组件，例如菜谱条目、食材行、步骤、家庭成员行；沿用现有项目层次，不因预览创建另一套状态管理。
- 不把 HTML 的 DOM、`dialog`、SVG sprite、`location.hash`、CSS container query、浏览器 API 或内存样例原样搬入小程序。图标采用同一套可编译到微信端的资源。
- 继续使用现有 `features/**`、鉴权、家庭代次、并发保护、私有媒体和错误映射。页面美化不能绕过服务端权限、幂等或校验。

### 4.1 统一组件与交互规则

具体页面遵循 [page-specs.md](page-specs.md)，共用以下规则（D-11 / D-12）：

- **按钮与入口**：同一任务区域只有一个最强主操作，通常用 `wd-button type="primary"`；次操作用 `type="info"` 或 `variant="text"`。删除/移除/退出家庭等有数据或权限后果的操作使用危险文案及危险样式，确认中说明对象和后果；退出登录是普通次操作。设置导航优先 `wd-cell` / `wd-cell-group`，不把所有入口堆成同等强度的大按钮。Wot v2 按钮变体用 `variant`，不照搬 v1 的裸 `plain` 属性。
- **表单**：优先 `wd-form` + `wd-form-item` 承载标签、必填说明和字段错误；2.4.0 使用 `model` / `schema` / `prop`，不是 v1 `rules`。可用官方 `FormSchema` 复用现有业务校验，不为 UI 重构强加 Zod。数字输入保留空值与原始文本语义，不能用计数器默认值把未知份数或数量初始化为 0/1。失败保留输入，指出具体字段/行和修正方法；提交后定位首个错误，不能只显示一段笼统 Toast。
- **标签与读屏**：可见字段标题、占位文字、`FormItem title` 和可访问名称不是同一个概念。微信使用官方支持的 `aria-role` 等属性，不能把 HTML `role="status/alert"` 源码直接算作小程序播报证据；H5 的语义另按其平台处理。核对 Wot 实际渲染的内部输入/按钮是否获得名称、状态和错误说明；把 ARIA 写在 Vue 组件外层不等于原生内部节点已关联。若当前包无法满足，记录限制，采用最小平台控件例外并实测，不修改第三方源码或虚构属性。
- **反馈**：首次读取用内容区加载；追加分页保留已有内容并在尾部反馈；写请求在触发区域显示忙碌并防重复提交。Toast 仅用于短暂、无需恢复操作的结果；字段错误留在字段旁，权限/冲突/未确认请求及可恢复失败使用持续可见文案和明确动作。同一任务不叠加多套加载动画，不用模态加载锁住整页等待 AI。
- **弹层**：无草稿的添加菜单可点遮罩关闭；含输入或写请求的弹层必须明确遮罩、返回和关闭行为，防止静默丢弃内容。底部弹层开启安全区，内容超高时内部可滚动，键盘不遮住当前字段及确认操作。`wd-popup` 使用 `v-model`，Picker 类是否使用 `v-model:visible` 逐组件核对；`root-portal` 按定位需要启用。懒渲染中的尺寸测量在显示后初始化；不要照搬 HTML `dialog`。
- **表单离开与恢复**：区分尚未提交的输入、已发送但结果未知的原请求、已确认成功三种状态。应用内主动离开或重新加载将丢弃输入时先说明并允许继续编辑；请求未知时恢复原操作 ID，不能把“再试一次”变成新的写入。系统关闭不承诺恢复尚未提交草稿；恢复持久化内容仍遵守身份与家庭范围，不能绕过隐藏/失权清理。
- **平台例外与样式**：原生导航、TabBar、分享、图片选择/预览和已存在的原生确认框可以保留；Wot 的 `open-type` 等能力已受支持时也可复用，不为统一颜色强制重写平台交互。优先 token、公开 props 和外部样式类；必要内部类覆盖须说明可访问性/平台原因、限定范围并验证当前版本，不把它变成后续组件的默认模板。

## 5. 页面模式

### 5.1 菜谱浏览

家庭上下文 → 一句主标题 → 搜索与“添加” → 全部/个人收藏 → 标签筛选 → 当前结果及分页 → 菜谱列表。

默认双列 `4:3` 图文条目，菜名在下方，时间与作者作次级信息，收藏为独立按钮。搜索保持家庭内有界标题/标签匹配与原有分页语义；服务端数据未拉全时，不把本地已加载数量展示为全家庭总量，不增加无后端契约的排序。窄屏或大字号发生挤压时改为单列，不能靠缩小到难读字号保住双列。

添加入口优先提供手动创建及已经交付的导入方式。没有权限或没有交付的功能不以可点击的假入口呈现。空家庭、无匹配、收藏为空、加载失败和下一页仍可搜索要明确区分。

### 5.2 菜谱详情与编辑

详情顺序：菜图 → 标签、全称、真实作者 → 可用的时间/份数 → 简介 → 食材 → 编号步骤 → 已交付的互动功能。未实现的评分和评论不显示样例或占位评分。

食材使用名称/原文与数量两列，保留备注与“适量”等未知数量。缺少基准份数时不提供假换算，缺少准备或烹饪时间时不显示 0 代替未知。总时长缺一部分时不把已知部分冒充总时长。

编辑沿用结构化食材字段、图片上传/审核和版本校验；未知字段不能因简化表单变成 0、空字符串或被删除。保留未完成保存、恢复请求、冲突、重新加载确认、图片失败与授权失效反馈。

底部固定操作只能提供已经有业务能力的动作，不能遮挡正文、系统手势或输入键盘。未交付计划/加购时不照抄 HTML 的“安排到一餐/加购”按钮。

### 5.3 微信登录、家庭引导与家庭管理

登录保持微信单一入口，清楚显示请求中、失败和重试；不引入密码注册或手机号必填。

家庭引导区分创建、已持有邀请和已有家庭；不增加多家庭切换。家庭页使用真实家庭名称、角色、成员和分组设置。所有者与普通成员权限保持当前规则：邀请、撤销、移除、转移、退出及后续解散各自展示和确认，不能因重排版遗漏已有能力。

原型中的头像汉字、总菜谱数、成员数和计划数不是接口字段保证；缺少可靠数据就省略，不为装饰新增统计接口。

### 5.4 AI 导入

输入 → 排队/解析或审核 → 成功/失败/取消。成功后已经自动保存，提供“查看菜谱”“核对并编辑”，不追加一次人为确认保存。

保留请求丢失恢复、任务恢复、真实状态查询、有限重试及取消含义。正式 AI/网络耗时不能用定时器假进度替代；不能承诺取消必定停止供应商计费。第三方处理说明、内容范围及保留期限保持真实。图片/网址方式随其工单交付，不因视觉稿提前开放。

### 5.5 后续计划、清单与互动

以下用于 #11–#16 的后续设计，不是本次既有页面重构的前置依赖：

- 计划：一周日期条加当天餐次列表，含早餐/午餐/晚餐/**其他**；同餐多菜；使用家庭本地日期，不能复制原型固定日期。目标份数属于计划快照。
- 清单：可选择多张共享清单，食材行操作、数量右对齐，已购独立分组；先完成 #12 的手动清单，再按 #13/#14 显式加购。
- 加购：未知数量不猜测；兼容单位才合并，保留原始贡献与幂等请求；部分完成可恢复。HTML 仅按名称去重的演示不满足生产规则。
- 评论：家庭内纯文本、分页、本人编辑/删除和所有者删除；不是样例评论常驻区。
- 评分：每人一个 1–5 整数评分，可改可撤销；平均值一位小数并带人数，零评分显示“暂无评分”。

### 5.6 导航分阶段交付

最终信息架构为“菜谱 / 计划 / 清单 / 家庭”。只有对应功能已交付才加入主导航。

已有页面重构可先采用“菜谱 / 家庭”两个真实可用入口，不因另外两页未交付而阻塞，也不新建空白计划/清单页。调整 TabBar 时一并核对 `navigateTo`、`switchTab`、`reLaunch`、返回、邀请续接、登录家庭守卫和页面隐藏后的敏感状态清除，不能只改 `pages.json`。

## 6. 交互与可访问性验收

- 320 / 375 / 390 / 430 逻辑像素宽度、常规和大字号：无页面横向溢出、关键文字截断、按钮重叠和内容遮挡。横向标签区可独立滚动。
- 控件有可理解的名称、标签和选中/禁用/忙碌状态；适用平台的屏幕阅读器能识别关键操作和异步结果。
- 普通正文对比度至少 4.5:1，适用的大字至少 3:1；必要图形/控件边界至少 3:1。不能用颜色单独传达错误、收藏或已购。
- 项目触摸目标要求至少 44 × 44 逻辑像素；这比 WCAG 2.2 AA 的 24px 最小目标要求更严格，不能混称标准最低值。
- 保留输入标签、键盘类型、粘贴、可读错误与恢复操作；H5 验证保留缩放和可见焦点。
- 使用轻量按下/切换反馈；不使用持续干扰动画。适用平台遵循减少动态效果设置。
- 覆盖正常、加载、空、失败、权限失效、请求未确认/恢复、共享编辑冲突、媒体失败状态；不是只验首页截图。

HTML 的 10px 导航、34px 标签按钮、模拟图片、临时表单和缺失状态不豁免这些验收要求。需要调整时以可访问性和真实业务为优先，并记录与视觉稿的差异。

## 7. 实施与证据

1. 设计/改版先读 `sources.md`、相关业务设计与实际代码；用 Refero 做参考锁定，按工单列出采用与不采用的内容。复用本基线足够时不重复生成三套方向。
2. Vue 页面使用 `vue-best-practices`、`uni-app`；Wot 组件选型、API、主题和排错使用 `wot-ui-v2`，执行 [miniapp/AGENTS.md](../../../miniapp/AGENTS.md) 的查询与证据流程：本地 `llms.txt` / `llms-full.txt`、CLI/MCP、Context7 与对应版本官方资料交叉核对实际安装包。涉及新共享逻辑才按需用其他 skill，不机械增加依赖。
3. 每个 UI 工单按 [issue-design.md](issue-design.md) 填写来源、当前事实、范围、状态矩阵、验收和真实依赖。没有新业务需求的视觉重构不修改云契约。
4. 生产改动运行 `task -d miniapp check`，以 `miniapp/Taskfile.yml` 实际定义为准；通过既有业务回归、类型检查、微信构建及边界/密钥检查。
5. 保存小程序实际渲染的页面/状态/屏宽/设备截图与差异说明；HTML/jsdom 自检只能证明原型交互，不能证明微信渲染或云验收。
6. 关闭工单前核对可访问性和手机安全区/键盘遮挡。工具不可用时记录缺失证据，不将其写成已通过；可开始实施与可关闭工单是两个不同判断。

## 8. 维护方式

这是 v1 基线。后续风格变更必须记录提出原因、依据、受影响页面和确认状态，并同步预览/规范/验收，不静默覆盖用户已认可的方向。技术兼容修正和可访问性修正可以在既有授权范围实施，但要在对应工单说明差异。

新增页面先复用这里的模式；新的重大交互或视觉选择必须补来源。不得引用“模型偏好”或“skill 推荐”代替用户需求、官方能力或实际产品参考。
