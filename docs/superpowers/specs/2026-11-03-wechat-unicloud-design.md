## 1. 意图与成功标准

以 Mealie 的核心业务为参考，重新开发一个供家庭成员共享使用的微信小程序。最终运行环境仅包含 uni-app、uniCloud 及外部 AI 服务，不依赖 Python、FastAPI、SQLAlchemy 或常驻自建服务器。

从空数据库开始，不迁移旧用户、菜谱、图片及历史记录，不兼容旧 REST API。用户能够创建或加入家庭，管理共享菜谱，使用 AI 导入内容，安排膳食和维护购物清单，并对家庭菜谱评论、评分。

成功的判断不是旧代码搬迁比例，而是核心业务闭环可用、家庭数据可靠隔离、AI 结果可校验和修改、成本可控制，并且新系统能够独立部署和恢复。

## 2. 已确认需求

以下内容来自用户明确确认：

1. 最终彻底下线 Python/FastAPI，不保留独立 Python 抓取或解析服务。
2. 网页内容和食材结构化可以改为调用 AI 服务，接收结果后保存。
3. 从空数据库开始，无历史数据迁移要求。
4. 去掉原 Mealie 的群组层，只保留用户、家庭及家庭成员关系。
5. 一个用户同一时间最多属于一个家庭，不做多家庭切换。
6. 首版包括微信登录、家庭管理、菜谱管理、AI 导入、膳食计划、购物清单、评论评分。
7. 家庭内共享，不做公开社区；成员身份及跨家庭访问在云端校验。
8. 评论可发表多条，本人可编辑、删除，家庭所有者可删除不当评论。
9. 评分为 1～5 星整数，每人每道菜谱一份，可修改或撤销；展示平均分、评分人数和评论列表。
10. 首版不做评论嵌套回复、点赞及举报系统。

## 3. 目标、非目标和禁止走向

### 3.1 目标

- 提供可真机使用的微信小程序，首版中文界面。
- 核心写操作集中于云对象，业务约束和家庭归属不依赖客户端自觉遵守。
- 文本、图片及可读取网址使用统一的 AI 解析结果契约。
- AI 或网络失败不破坏现有菜谱，不产生重复保存和无上限重试。
- 家庭共同维护计划、购物清单；处理并发和重复请求。
- 数据、媒体及关键配置有明确的备份和恢复方式。

### 3.2 非目标

- 现有 Nuxt Web 端的迁移、维护或接口兼容；首版不交付 H5、App、uni-admin 或公开运营后台。
- 旧数据库迁移、旧登录体系、LDAP/OIDC 和长期 API token 兼容。
- 复刻全部 Mealie 功能；不包含 MQTT、Webhook、自动化平台集成等旧集成。
- 自部署 AI 模型、实现通用网页爬虫、承诺绕过登录/付费墙/反爬限制。
- 公开菜谱广场、跨家庭分享、支付、营养计算器、食材密度数据库、AI 自动配餐。
- 首版实时推送、逐 token 展示、离线写入及多设备实时协同编辑。

### 3.3 禁止走向

- 不能为了复用旧能力而重新引入 Python/FastAPI 运行依赖。
- 不能把任意 AI 输出直接作为数据库指令或可信权限数据执行。
- 不能只在前端隐藏按钮，而不做云端身份、家庭和资源归属验证。
- 不能以公开永久图片 URL 替代私有家庭文件的授权设计。
- 不能在新应用尚未独立验收时删除旧代码、数据或关闭用户的现有服务。

## 4. 考虑过的方案及选择

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| uni-app 小程序 + uniCloud 入口 + 保留 FastAPI/SQL/Python 解析 | 可复用现有后端，迁移风险较低 | 仍需维护 Python 服务、身份桥接及两套环境 | 用户已排除，不符合最终完全去 Python 的目标 |
| uni-app + uniCloud 完整重建 + 外部 AI 解析 | 无旧 API 和旧数据兼容负担，最终统一为云端一体应用 | 需要重写页面、数据访问、权限和核心业务 | 用户选择；本文采用 |

在完整重建方案内，设计建议核心业务采用云对象，而不是把所有数据库操作放在 clientDB：本应用有家庭隔离、成员变更、购物合并、评分唯一性和 AI 成本控制，集中服务层更便于验证。clientDB 不作为首版业务数据的直接入口。

## 5. 设计者建议及实施者决策边界

除第 2 节外，本文的具体规则原由设计者提出，现随整份文档获得批准；应保留这一来源区别，不能当作用户最初主动提出的要求。

### 5.1 本设计建议采用的默认值

- 新工程放在仓库新增的 `miniapp/` 内，保持旧 `frontend/`、`mealie/`、生成文件和依赖不变。
- 首版仅微信登录；不采集非必要手机号，不提供密码账户。
- 用户登录后可以暂时没有家庭；创建家庭或接受邀请后才能访问业务数据。
- 家庭角色仅 `owner` 与 `member`，不使用 uni-id 全局 `admin` 代表家庭所有者。
- 收藏是用户个人偏好，只有本人可管理；不将评分或收藏混为菜谱归属。
- 首版不对外分享家庭菜谱或原始导入材料。

共享编辑与删除权限集中在第 8.2 节，评论和评分的格式及展示默认值集中在第 11 节，AI 校验后的保存默认值集中在第 9.2 节。这些同样属于本次批准的设计默认值。

### 5.2 可以由实施者自行确定

- 组件库、视觉风格的基础实现、分页大小、输入长度上限和初始配额等可配置常量。
- 满足本文约束的 uniCloud 云厂商、服务空间地域和受支持运行时；必须记录验证结果，不能假定不同云能力完全相同。
- 满足结构化文本和图片解析要求、地域可达和使用条款的首个 AI 供应商及模型；供应商账户由部署者提供。
- 在 `uni-ai` 与供应商官方 HTTP 接口之间选择适配方式；不以更换供应商为由改变结果契约。
- 私有云存储或兼容的私有扩展存储的具体选型、日志与测试工具。
- 工程内模块文件名、有限枚举和底层数据库调用写法。

### 5.3 能力不足时的边界

如果平台无法提供可靠的事务/条件写、私有文件访问或可用 AI 能力，实施者必须报告约束，而不是把数据公开、改回 Python 或悄悄删减首版功能。云账户、密钥、域名和备案属于部署前置条件，并非本设计已具备的资源。

## 6. 技术架构与工程边界

### 6.1 客户端

采用 uni-app Vue 3 + TypeScript。使用支持微信小程序的组件，不复用 Vuetify、Nuxt 插件、浏览器 Axios 适配器或依赖 DOM 的组件。

页面导航、生命周期、网络、存储、上传和图片预览使用 uni-app/微信兼容能力。业务 composable 依赖统一的客户端服务接口，不在页面散落数据库查询或供应商调用。

### 6.2 云端

- 身份：uni-id-pages、uni-id-co、uni-id-common。
- 配置：uni-config-center 或云端受控配置；密钥不进入小程序包、示例代码或版本库。
- 入口：按家庭、菜谱、导入、计划、购物、互动划分云对象。
- 业务模块：共享鉴权、校验、幂等、任务状态、食材规范化和购物计算逻辑。
- 数据层：统一封装带家庭条件的数据访问；平台 SDK 不直接散落到所有业务方法。
- 任务：受控的定时 worker 和清理任务；不部署常驻进程。

云端可优先采用 TypeScript；按当前官方文档，HBuilderX 5.25 起支持本地编译后部署，云端运行的仍是 JavaScript。实施时锁定实际工具版本与云运行时，不能假定客户端 TS 配置自动适用于云端。

### 6.3 工程隔离与生成文件

工程目录及旧工程保留规则见第 5.1 节。

新工程独立管理依赖与校验命令。不手改原 `frontend/app/lib/api/types/` 或 Pydantic 生成文件，不运行旧代码生成器为新模型生成接口。

## 7. 数据模型与关键不变量

### 7.1 集合与约束

集合名为建议名称。业务集合带服务端生成的创建/更新时间；可编辑共享记录带版本号。

| 集合 | 主要内容 | 关键约束 |
| --- | --- | --- |
| `uni-id-users` | 微信登录身份、昵称、头像、账户状态 | 不存家庭所有者的全局管理员角色 |
| `families` | 名称、所有者 UID、状态 | 活跃家庭恰有一个有效所有者 |
| `family_members` | UID、家庭 ID、角色、加入时间 | 以 UID 为唯一成员槽；一个用户最多一个活跃家庭 |
| `family_invitations` | 家庭 ID、邀请凭据摘要、过期时间、使用状态 | 高熵单次凭据，限时有效；不存明文可用邀请码 |
| `recipes` | 家庭 ID、作者、标题、说明、份数、食材、步骤、时间、图片引用、来源 | 家庭归属不可由普通更新修改；家庭内有效 slug 唯一 |
| `recipe_favorites` | UID、家庭 ID、菜谱 ID | 用户与菜谱唯一；只对本人暴露收藏关系 |
| `recipe_comments` | 家庭 ID、菜谱 ID、作者、纯文本内容 | 多条评论；独立集合和分页 |
| `recipe_ratings` | 家庭 ID、菜谱 ID、UID、1～5 整数 | 家庭、菜谱、UID 组合唯一，可使用确定性 ID 保证 |
| `meal_plans` | 家庭 ID、本地日期、餐次、菜谱 ID、目标份数、标题快照 | 每天每餐允许多道菜；不使用日期转换暗改用餐日 |
| `shopping_lists` | 家庭 ID、名称、状态 | 支持多张清单，成员共享 |
| `shopping_items` | 清单 ID、家庭 ID、食材键、数量、单位、备注、勾选、来源 | 独立条目以支持并发更新；数量来源可追溯 |
| `shopping_additions` | 清单、来源操作、请求 ID、份数和贡献快照 | 一次加购操作可恢复、可去重 |
| `import_jobs` | 请求者、家庭、输入引用、状态、尝试次数、租约、结果菜谱 ID、错误 | 同一次幂等请求只有一个任务、最多保存一份菜谱 |
| `media_files` | 存储引用、家庭、上传者、用途、状态、大小/类型 | 禁止绑定其他家庭的文件；临时材料有清理期限 |
| `ai_usage` | 家庭、UID、任务、供应商、尝试、token/费用计量 | 不存密钥；无法获取精确费用时记录估算标识 |

### 7.2 存储形态与输入边界

菜谱步骤和食材明细可以嵌入有上限的菜谱文档；评论、评分、计划和购物条目独立存储。食材保存原文、规范名称、可选数量、可选标准单位和备注，不要求建立全局食材字典。

- 数量：字符串数量如“适量”不得强制转成 0。
- 图片：只保存受控文件标识，不长期保存已过期的签名 URL；授权和清理规则见第 12 节。
- 大小：元数据、步骤数、图片数、JSON 大小和字符串长度均有边界。

### 7.3 索引

索引至少覆盖家庭内菜谱分页/搜索、家庭内 slug 唯一、成员 UID 唯一、评论分页、评分唯一、日期餐次查询、清单条目及待处理任务/租约。索引定义和唯一性要以目标云实测结果为准。

## 8. 家庭生命周期与权限

### 8.1 创建、邀请与退出

- 创建家庭时，在受保护的一次操作中创建家庭和唯一成员槽，创建者成为所有者；并发创建/加入只能成功一次。
- 所有者创建单次邀请，建议有效期 24 小时，可以撤销。接受邀请时原子检查凭据、有效期、家庭状态和用户无家庭条件，再消费邀请和创建成员关系。
- 已有家庭的用户不能直接接受其他家庭邀请，不自动迁移、合并或搬运数据。
- 普通成员可退出；所有者可移除普通成员。所有者离开前须转移所有权给当前成员，或解散家庭。
- 所有权转移应同时更新家庭和相关成员角色；不能产生零所有者或双所有者窗口。
- 退出/移除立即撤销后续业务和文件授权；旧签名链接在其短有效期内可能仍有效，不能宣称可即时撤销所有已签发链接。

### 8.2 权限矩阵

| 操作 | 普通成员 | 家庭所有者 |
| --- | --- | --- |
| 读取家庭菜谱、计划、清单、评论与评分 | 允许 | 允许 |
| 创建、编辑菜谱，维护计划和清单 | 允许 | 允许 |
| 删除菜谱 | 仅本人创建 | 家庭内全部 |
| 收藏、评分 | 只修改本人关系 | 同左，不代改他人评分 |
| 评论新增、编辑、删除 | 本人评论 | 可删除他人评论，不编辑他人内容 |
| 邀请、移除成员，修改家庭信息 | 不允许 | 允许 |
| 转移所有权、解散家庭 | 不允许 | 允许 |

- **业务请求：**所有业务入口验证 uni-id token，再查询当前成员关系及家庭状态。不能只依赖 token 中可能过期的角色或客户端提交的 `familyId`。先确定家庭条件再读取目标对象，不泄露其他家庭对象是否存在。

- **后台入口：**任务 worker 不以普通用户 token 续期作为后台身份：创建任务时固定请求者和家庭，执行前、保存前重新核对请求者仍是该家庭成员。定时触发云对象不会执行 `_before`，必须有专门的系统入口和授权路径，不能靠外部可伪造的入参冒充定时任务。

- **数据库访问：**业务 clientDB 权限默认关闭；服务端使用传统 MongoDB API 时，Schema 权限与校验不能视作自动生效，必须在服务层显式执行。若使用 JQL，明确设置可信上下文，仍保留跨资源业务检查。

### 8.3 历史内容和删除

**成员退出：**其已提交共享菜谱、计划、评论和评分留在原家庭，作者显示为“已离开成员”；退出者不能继续读取或修改。私人收藏删除。后台不能向新家庭泄露旧家庭内容。

**账户注销：**先处理所有者转移/解散，再删除其收藏、评论、评分、个人信息及临时导入材料；共享菜谱、计划和购物记录保留为家庭数据并匿名化作者。注销流程需可恢复，并与最终隐私协议一致。

**家庭解散或菜谱删除：**先标记不可访问，再以幂等清理任务处理关联数据和文件。对已删除菜谱的计划保留标题快照并标记来源不可用；购物条目保留已形成的食材快照；删除菜谱不静默修改已安排的餐次或已采购数量。文件生命周期的补偿机制见第 12 节。

## 9. AI 导入契约与任务执行

### 9.1 输入边界

- 文本：粘贴菜谱、食材说明或做法。
- 图片：上传菜谱照片或截图，首版不支持视频/音频。
- 网址：交给明确支持网页读取的 AI 服务/配套托管读取能力，不自行构建通用抓取器。

- **读取能力：**普通聊天模型接收 URL 不代表读过网页；联网搜索也不等于能读取指定页面。读取失败必须明确报告，并提供粘贴正文或上传截图入口，不允许编造菜谱伪装成成功导入。

- **访问边界：**不支持绕过登录、付费墙和平台访问限制。仅接受 HTTP/HTTPS 公网网址；云端与供应商适配器不跟随未经验证的私网/本地/元数据地址，不下载 AI 返回的任意附件或图片 URL。

### 9.2 标准结果

供应商适配器向业务层交付版本化的 `RecipeImportResult`：

- `schemaVersion`、标题、可选说明、可选份数、可选准备/烹饪时间。
- 食材数组：原文、名称、可选数值数量、可选单位、可选处理说明。
- 有序步骤数组，必要时有来源中实际提供的图片引用。
- 输入来源、实际读取状态、可选警告；来源记录由云端与任务输入核对，不能仅信 AI 声明。
- 原文未提供或无法可靠确定的字段为空，不要求估算营养值、份数和数量。

**校验与素材访问：**

- 结果必须经过云端结构校验、字段白名单、大小约束和业务验证。即使供应商支持 JSON Schema/工具调用也不免除验证。
- 网页与图片文字只当待提取数据，不当作系统指令；AI 没有写数据库、发起邀请或任意执行工具的权限。
- 图片返回的食材数量、单位和来源归属需同样校验。素材访问以受限临时 URL 或供应商支持的安全传输方式提供，禁止向模型暴露云存储管理密钥。文件授权见第 12 节。

**保存默认值：**

- AI 校验成功后自动保存为可编辑菜谱，不要求用户再次确认才能保存；不完整但仍满足最小结构的结果附带提示，不自动公开到家庭以外。
- 首版每个导入请求最多生成一道菜谱；多菜谱输入要求用户选择或分开导入。
- 保存的幂等与终态约束见第 9.3 节。

### 9.3 异步执行与幂等

**提交与调度：**

客户端提交后只获取任务 ID，查询任务状态，不等待整个 AI 调用完成。状态为 `queued`、`running`、`succeeded`、`failed` 或 `cancelled`。

首版建议由定时 worker 扫描任务：基础调度按每分钟运行设计，不承诺秒级开始；客户端显示“等待解析”，页面关闭不取消任务。若所选平台支持更低延迟的可靠触发，可以由实施者优化，但仍需扫描兜底。

**领取、执行与恢复：**

- worker 通过条件写获取有期限的任务租约，限制批量数和并发，不能重复处理同一有效租约。
- 单次供应商调用和一次 worker 批次都设置小于平台上限的明确超时。AI 请求期间不持有数据库长事务。
- `running` 租约过期可以被恢复；终态结果不可被旧 worker 覆盖，保存时校验任务版本/租约及家庭成员关系。
- 网络错误、限流和可恢复服务错误允许有限重试；默认最多初次加两次重试，退避并计入预算。内容无法读取或无法识别，不无限重试。
- 不使用 `return` 后继续执行的悬空 Promise，不依赖平台实例保留时间提供后台可靠性。

**保存与取消：**

- 菜谱保存采用由任务确定的唯一结果 ID，并在事务或等效原子协议中固定任务结果，避免“已写菜谱但任务未完成”导致重复创建。
- 取消只阻止后续保存，不承诺供应商已执行请求可撤销或退费；取消与完成竞争必须有唯一终态。

**客户端反馈：**不把仅发给客户端的 AI 流式内容当作可信持久化结果。首版不依赖 SSEChannel/uni-push；如后续引入，只用于改善反馈，最终数据仍由云端验证、持久化。

### 9.4 成本与隐私

**限额与结算：**部署配置提供每用户/家庭的每日任务限额、并发上限、输入大小、输出 token、供应商超时和全局停用开关。创建/领取任务时原子预留可用配额，结束时结算，避免并发绕过额度。

**预算保护：**记录任务各次供应商尝试、用量和错误，不承诺跨供应商“恰好计费一次”。重试前检查剩余额度；全局预算超过阈值后停止新调用，已保存数据和手动编辑不受影响。

**留存与告知：**原始输入和供应商原始响应仅用于短期排障，设计建议最长保留 7 天，随后清理；日志不默认打印全文。永久保留经过校验的菜谱、必要来源及解析版本，隐私告知中说明第三方 AI 处理。

## 10. 菜谱、膳食计划与购物计算

### 10.1 菜谱与搜索

菜谱有标题、说明、原始/规范化食材、步骤、可选份数和时间、图片及来源。支持手动创建和 AI 导入后的编辑。缺少份数不阻止保存，但不能进行未知基数的自动份数换算。

首版搜索限定家庭内，对标题和受控标签做有界匹配与分页，不承诺中文全文检索、模糊语义搜索或兼容旧 Mealie 查询语言。实施者应评估索引和扫描上限，不以客户端查询后过滤实现家庭隔离。

### 10.2 膳食计划

使用家庭约定的本地日期和早餐/午餐/晚餐/其他餐次，首版默认北京时间；日期以 `YYYY-MM-DD` 表示，不用 UTC 时间戳隐式换日。

同一餐次可安排多道菜，保存菜谱引用、标题快照及目标份数。引用必须属于当前家庭。更改计划不自动反向修改购物清单；用户显式执行“加入清单”。

### 10.3 购物清单

**数量计算与合并：**

- 从菜谱或计划加入，支持目标份数；数量按目标份数/菜谱基准份数计算。
- 原始数量未知、份数未知或单位不兼容时，不猜测；保留原文并提示手动确认。
- 只对名称规范键及兼容单位一致的条目合并。首版支持确定的同量纲换算，如 kg/g、L/mL；不把体积转换成质量，不猜测“一勺”的容量或食材密度。
- 不调用 AI 执行加减、份数缩放或数据库汇总。

**加购幂等与恢复：**

- 每次加购保留操作 ID、原始贡献及来源快照；重复提交同一请求不重复增加数量，用户主动再次加购使用新操作 ID。
- 批量加购采用可恢复操作记录，逐项使用幂等键/原子写保证重试不会重复累计；部分完成时清晰展示处理状态，不能伪装为全部成功。

**共享编辑：**

- 勾选为条目级原子更新，不以整张清单覆盖保存，避免不同成员勾选互相覆盖。
- 共享记录编辑采用版本检查；冲突时提示刷新，不默默覆盖对方修改。

## 11. 评论和评分

### 11.1 评论

评论仅对当前家庭成员开放，纯文本、不接受 HTML、有限长度、分页展示。编辑使用版本检查；新增、编辑和删除权限以第 8.2 节权限矩阵为准。

### 11.2 评分与统计

**评分记录与展示：**

- 每位用户每道菜谱最多一个 1～5 的整数评分，提交相同评分幂等，修改覆盖本人评分，撤销删除本人评分。菜谱作者也可以评分，不禁止自评。
- 平均分按有效评分的总和/人数计算，显示一位小数；评分人数为 0 时显示“暂无评分”，而不是 0 星。
- 客户端不能传入平均分、评分人数或他人的 UID 作为更新目标。

**统计口径与查询：**

首版以评分记录为唯一事实来源，云端读取时做限定家庭和菜谱 ID 的有界聚合，不在菜谱记录维护容易漂移的平均分缓存。列表按当前页菜谱批量聚合，避免逐条请求。以后确有性能需求再增加可修复缓存。

成员退出后仍保留其历史评分计入统计；注销时删除其评分后重新按记录聚合。其他历史内容和注销规则见第 8.3 节。

### 11.3 功能边界与内容安全

不做公开评论、回复树、点赞、举报或评分权重算法。按照微信发布要求处理用户生成文本/图片内容安全；具体审核接口由实施者按主体能力接入，不能把家庭私有作为免审核的假设。

## 12. 文件授权与删除一致性

### 12.1 上传与访问授权

所有上传先在云端申请用途、类型、大小及家庭约束，再使用受控上传凭据。上传完成后验证文件元数据及归属，才允许关联到菜谱或 AI 任务。

客户端提供任意 URL 或文件 ID 不构成合法绑定授权。下载链接必须由云端在核对当前成员及文件用途后签发，使用短有效期；原始解析材料仅任务发起者和受控 worker 可访问，不默认暴露给其他成员。

### 12.2 存储与处理能力

发布前确认所选云/存储真实支持所需的私有文件策略。若内置云存储不能满足，选择私有扩展存储；数据库 Schema 不会自动保护公开文件地址。图片处理使用平台能力、兼容 Node 的轻量实现或受控存储服务，不恢复 Pillow 依赖。

### 12.3 文件生命周期与补偿

文件、数据库和外部 AI 不在一个原子事务内：采用临时上传状态、业务关联状态、待删除状态及定期清理补偿，避免孤立文件和删除中断。第三方远程图片不自动下载；用户可上传，或在明确许可且安全校验后另行接入受控导入。

## 13. 部署、安全与可观察性

### 13.1 环境与发布

- 开发、测试、生产服务空间和密钥隔离；只部署版本库中的配置模板，不提交真实凭据。
- 在微信后台配置当前厂商实际的 request/uploadFile/downloadFile 等合法域名；不以开发工具的跳过校验作为发布方案。
- 校验微信主体、类目、备案、隐私保护指引、AI 服务地域与使用条款。选择供应商时验证云端实际可达性，不假定本机可调用即生产可调用。

### 13.2 调用安全与可观察性

- 启用家庭/用户级限流；日志关联请求、任务、家庭及供应商尝试，个人信息脱敏。
- 定时清理入口只允许平台触发；若需要 HTTP 回调，必须独立验签、防重放、按供应商任务映射校验，首版不以未验签回调驱动入库。
- 关注错误率、任务排队/租约恢复、AI 失败率和费用、数据库慢查询、孤立文件及清理积压。

### 13.3 备份恢复与许可

- 备份范围包括数据库、文件清单/对象、Schema、索引及恢复所需配置；真实密钥另行安全备份。上线前演练一次空环境恢复。
- 参考或复用旧仓库代码时审查 AGPL-3.0 和依赖许可，不将“重新建目录”视为免除许可义务。

## 14. 验收与测试边界

以下是验收条件和测试覆盖要求，不表示相应场景已执行或已通过。

### 14.1 必须通过的业务场景

1. 新用户登录、创建家庭、所有者邀请第二位用户，双方看到同一家庭菜谱。
2. 并发创建/接受邀请不能让一个用户加入两个家庭；过期、重复、撤销邀请正确处理。
3. 第三个用户属于另一家庭，猜中菜谱、任务、清单、评论、文件 ID 也不能访问或修改。
4. 移除成员后，其旧登录态不能再访问家庭；转移所有权过程保持唯一所有者。
5. 手动菜谱创建、编辑、搜索、收藏及图片授权完整可用。
6. AI 文本和图片解析保存可编辑菜谱；可读取网址成功，不可读取网址明确失败且可改用正文/截图。
7. AI 输出损坏、截断、缺字段、恶意文本、越界数量或伪造归属时，不产生未校验的正式菜谱。
8. 任务超时、worker 中断、客户端断网、重复提交、取消和成员退出期间，不重复保存且终态一致。
9. 配额在并发下不可绕过；达到上限时手动菜谱等非 AI 功能仍可用。
10. 计划按正确日期、餐次和份数显示；购物加购、单位换算、来源追踪、重试及多人勾选结果正确。
11. 评论作者与所有者权限正确，跨家庭拒绝；评分创建/修改/撤销唯一且平均分正确。
12. 菜谱删除、家庭解散及注销流程能从中断恢复，受保护文件不会因记录删除遗漏而继续公开。
13. 在微信真机上验证登录、上传、任务查询、弱网重试和合法域名；开发工具成功不能代替真机验收。

### 14.2 测试层次

- 纯业务单元测试：结果校验、单位/份数计算、合并键、权限矩阵、状态机。
- 云端集成测试：事务与唯一性、并发成员加入、任务租约、购物幂等、评分聚合、文件授权。
- AI 供应商契约测试：固定文本/图片/网址样本，区分有来源提取和无依据生成；日常测试使用受控 fixture，不默认消耗真实额度。
- 小程序端到端及真机测试：至少两个家庭、多个账户、断网重进和成员移除。
- 部署恢复验证：空服务空间初始化、Schema/索引安装、定时任务配置、私有文件与备份恢复。

## 15. 交付阶段与停止条件

本节仅定义设计层面的交付顺序，不是实施任务清单。

1. 平台能力验证：云空间、身份、事务/条件写、私有文件、AI 文本/视觉/网址读取。依赖不满足时先报告，不搭建替代 Python 服务。
2. 身份与家庭隔离：登录、成员唯一性、邀请、所有权和权限测试。
3. 手动菜谱闭环：菜谱、搜索、收藏、私有文件。
4. AI 导入闭环：结果契约、持久化任务、成本和失败恢复。
5. 计划与购物：确定性计算、共享编辑、批量加购幂等。
6. 评论评分及全链路验收：归属、聚合、内容安全、注销/清理、恢复演练。
7. 微信体验版和正式发布：域名、备案、隐私和审核材料齐全后进行。

本文批准后才编写实施计划；实施计划不等同于自动获得生产部署、付费、提交代码或关闭旧服务的授权。旧服务何时停用另由用户决定，不自动删除旧代码。
